# 페이즈별 테스트 계획서 schema + TC ID 컨벤션

> qa-planner 8단계 (페이즈별 테스트 계획서 병렬 생성) 단일 출처. 본문에서는 본 파일로 위임한다.

---

## 병렬 Write 지침 (필수)

> ** 모든 페이즈 테스트 계획서는 파일 간 상호 의존이 없으므로, 단일 응답 메시지 안에서 Write 도구를 N회 병렬 호출한다. 순차 Write는 금지.**

> ** 슬러그 매칭 필수**: 테스트 문서의 `{slug}`는 dev-planner의 개발 문서 슬러그와 **정확히 일치**해야 한다. 3단계에서 Read한 dev `phase_files` 경로에서 정규식 `phase-(\d+)-(.+)\.md$`로 `{N}`과 `{slug}`를 추출하여 그대로 사용한다.
> - 예시 (055): dev `phase-2-auth.md` → test `phase-2-auth-test.md`
> - 예시: dev `phase-4-apply-v1.md` → test `phase-4-apply-v1-test.md`
> - 금지: 슬러그를 임의로 변경하거나 번역/축약 — 파일 쌍 매칭이 깨짐.

**경로:** `{workspace_root}/{{config.outputDir}}/plans/{task_number}/phases/phase-{N}-{slug}-test.md`

---

## 페이즈 테스트 계획서 스키마 (7섹션)

````markdown
# Phase {N} 테스트 계획 — {페이즈명} ({slug})

## 1. 페이즈 테스트 메타
| 항목| 값|
|------|-----|
| 페이즈 번호| {N}|
| 페이즈명| {한글명}|
| slug| {slug}|
| 의존 페이즈| {N-1} 또는 —|
| 참조 개발계획| `../phases/phase-{N}-{slug}.md`|
| 참조 루트 테스트 계획| `../{task_number}_test_plan.md`|
| 이 페이즈 TC 수| {N개}|
| 예상 테스트 실행 시간| {Nm}|

## 2. 검증 범위
이 페이즈가 커버하는 Task 목록 (개발계획 §7):

| Task ID| Task 제목| 대응 TC 수|
|---------|---------|:---------:|
| P2-T01| 로그인 페이지 렌더링| 2|
| P2-T02| OTP 발송 엔드포인트| 4|
| ...|

## 3. Task ↔ TC 매핑 테이블
**모든 Task는 최소 1개 TC로 커버되어야 한다.**

| Task ID| 대응 TC ID (1:N)|
|---------|-----------------|
| P2-T01| TC-WV-CTRL-001, TC-WV-CTRL-002|
| P2-T02| TC-WV-CTRL-003, TC-WV-CTRL-004, TC-WV-SVC-001, TC-WV-SVC-002|
| P2-T03| TC-WV-CTRL-005, TC-WV-CTRL-006, TC-WV-SVC-003|
| ...|

## 4. 자동 측정 가능 품질 항목 (TC 미생성)

> dev-plan 페이즈 §9 DoD 는 develop 수렴 루프 종료 판정표이지 TC 매핑축이 아니므로 *DoD ↔ TC 매핑* 은 작성하지 않는다. 대신 본 페이즈에서 *자동 측정 가능*한 품질 게이트 항목을 분류 (TC 본체와 분리).
> 자동 측정 불가한 검증 항목(SecureKeypad 평문 DOM 미노출 등)은 §5 TC 본체로 흡수 (Task ↔ TC 매핑에 포함).

| 자동 측정 항목| 측정 방식| 통과 기준|
|--------------|----------|----------|
| 테스트 커버리지| 언어팩 빌드 도구| 80% 이상|
| 설정 하드코딩 없음| grep 패턴| 매치 0건|

언어별 자동 측정 항목은 언어팩 `docs/agents/qa-planner/references/test-schema-lang.md`(있으면)를 참조한다.

## 5. 테스트 케이스

### 5-1. 자동 TC 본체 (qa-tester 파싱 대상)

> qa-tester가 이 섹션의 TC를 정규식으로 파싱하여 실행한다.
> - TC ID: `^####\s+(TC-[A-Z]+-[A-Z]+-\d{3}):\s+(.+)$`
> - 그룹 헤더: `^###\s+\[([A-Z-]+)\]\s+(.+)$`

### [{그룹ID}] {그룹명}

#### TC-{프로젝트약어}-{그룹약어}-001: {테스트 케이스 제목}
- **Priority**: P0/P1/P2/P3
- **Type**: Unit/Integration/E2E
- **Target**: {대상 클래스#메서드 또는 엔드포인트}
- **Mapped Task**: {Task ID — P{N}-T{nn}} **필수**
- **Preconditions**: {사전 조건}
- **Test Steps**:
 1. {단계 1}
 2. {단계 2}
- **Expected**: {기대 결과}
- **Test Data**: {정상값 / 경계값 / 무효값}

#### TC-{프로젝트약어}-{그룹약어}-002: {다음 TC}
...

### [{다음 그룹ID}] {다음 그룹명}
...

### 5-2. 기능 검증 체크리스트 (FE 페이즈 한정 — 기능 검증 공식 게이트)

> 페이즈 = 화면 1개 검수 단위 (R9 정합). 자동 TC가 커버하지 못하는 사람 검수 영역.
> qa-tester는 이 섹션을 **파싱하지 않는다** (체크박스 상태는 검수자가 수동 표시).
>
> **본 §5-2 가 *시나리오 C 기능 검증 공식 게이트*이다.**
> - `/develop` 자동 모드에서 BE·FE 페이즈가 동시 디스패치되며 자동 진행되는 동안, **페이즈 종료 시점에는 검수 게이트가 없다.**
> - 검수는 **모든 페이즈 종료 후 1회**, 사용자가 본 §5-2 체크리스트를 들고 브라우저에서 직접 수행하여 통과 여부 결정.
> - 기본 모드에서도 본 §5-2 는 페이즈 종료 시점 자가 점검에 활용 가능하나, *공식 기능 검증 게이트* 의 의미는 자동 모드에서 가장 강하다.
>
> **작성 조건:**
> - FE 페이즈(slug `fe-*`) → 작성 필수
> - R10 미적용 풀스택 단일 페이즈 + 화면 있음 → 작성 필수
> - BE 페이즈(slug `be` / `be-*`) → 작성 안 함 (브라우저 검수 대상 없음)
> - REST API / Batch / Daemon / Library / Proxy / 단일 서비스 → 작성 안 함

**대상 화면**: {페이즈 §1 메타의 화면 컬럼과 일치 — 단일 화면 또는 동일 페이즈 내 화면 1~N개}

**범용 검수 항목:**
- [ ] 화면 진입 시 의도된 레이아웃 (반응형 PC/모바일 — 프로젝트 정책 따름)
- [ ] 입력 필드 포커스 이동·탭 순서 자연스러움
- [ ] 에러 메시지 사용자 친화적 (모호하지 않고 행동 유도)
- [ ] 로딩 인디케이터 표시 (≥ 500ms 응답 시점)
- [ ] 화면 전환 깜빡임/잔상 없음
- [ ] 빈 상태(empty state)·예외 화면 안내 적절성
- [ ] 핵심 인터랙션 1회 직접 수행 (예: 로그인 시도·버튼 클릭·폼 제출)

**페이즈별 특수 검수 항목** (브리프 §8 또는 dev-plan 화면 명세에서 도출 — 자동 TC와 중복돼도 사람도 한 번 봄):
- [ ] {예: SecureKeypad — 평문 DOM 미노출(자동 NEGATIVE) + 마우스/우클릭/드래그 시도해도 평문 노출 없음}
- [ ] {예: 외부 SSO — 토큰 만료 후 재진입 흐름이 사용자 혼란 없이 처리되는가}
- [ ] {예: 마법사 다단계 화면 — 단계 간 뒤로가기/취소 시 입력값 보존 정책 일관}
- [ ] ...

**검수자**: 사용자 본인 (자동 모드 기능 검증) / 개발자 본인 + 기획자 (기본 모드 페이즈별 자가 점검)
**검수 시점**:
- **자동 모드 (시나리오 C)** — *모든 페이즈 종료 후 1회* 기능 검증. 페이즈 종료 시점에는 검수 게이트 없음. 본 §5-2 체크리스트가 *공식 기능 검증 게이트*.
- **기본 모드** — 페이즈 N 완료 자가 점검 (자동 TC Green + 수동 체크리스트 통과). 사용자 발화 *다음 페이즈* 트리거 직전 자율 활용.
````
