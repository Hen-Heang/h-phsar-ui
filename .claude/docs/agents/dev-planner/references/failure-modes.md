# Failure Modes & Final Checklist

> Single source for the self-check after Writing the dev-planner outputs (root/phase documents + meta JSON).

---

## Failure Modes To Avoid

- **Reinterpreting the brief**: overturning what brief §2 decided as "개발 유형: 신규" with "maybe it's actually an extension" → the brief is a contract; respect it. If you have an opinion, only record it as an assumption in §4 premises.
- **Halting when a brief section is missing**: aborting the agent run when a specific §N of the brief (e.g. §4 business↔code mapping) is empty or absent → **do not halt.** Record the corresponding plan section as the single row `| — | 해당 없음 (브리프 §N 미작성) | — |`, and add a "브리프 §N 보강 후 재계획 필요" item to the root §4 premises/assumptions. Only in the extreme case where both brief §3-4 (affected tables) and §11 (implementation order) are empty do you abort (guide the user to redo dev-interview).
- **Asking for scope separately**: asking the user for the scope identifier → it must be reverse-matched automatically from brief §2·§3.
- **Over-partitioning phases**: mapping every §11 step 1:1 to a phase → apply heuristics R4/R5/R7.
- **Under-partitioning phases**: bundling a large brief of 10+ steps into a single phase, or exceeding 4d per phase → violates **R7** (recommended count 4~7) or **R6** (recommended 1~3d per phase). Re-evaluate the brief's scale and re-partition.
- **Strong coupling between phase documents**: phase B endlessly quoting phase A's detail sections → push the content into the root's §6/§7/§8 (global) and keep phase documents concise with "루트 §N 참조".
- **Task abstraction**: a vague Task like "Controller 구현" → make it concrete like "POST /auth/login/otp 엔드포인트 추가 (0.5d)".
- **Writing a §검증 방법 (test files·coverage) section in a dev-plan phase**: a dev-plan phase document writes only up to §9 완료의 정의(DoD) = the develop convergence loop's end *verdict table*, and does not create a §검증 방법(테스트 파일·커버리지·통과 기준) section. §9 DoD is merely a table that judges completion via acceptance criteria + verdict-type tags (객관/자동·주관/surface), not a test-code/coverage spec. Tests, regression, coverage, and pass criteria are all delegated to the qa-plan per-phase test documents. Phase completion is judged by the convergence loop's owner (the caller — a person or dev-autopilot) checking against §9 DoD.
- **Reading config files**: opening YML/Properties — absolutely forbidden.
- **Querying real data**: PostgreSQL `SELECT * FROM ...` — metadata only.
- **Dropping the meta JSON legacy key**: omitting the `work_request` alias makes qa-planner unable to read its input and fail silently → always keep the dual keys.
- **Thin partition rationale**: not recording in root §5-2 which rule was applied and how → makes it hard when the user asks for regrouping.
- **Skipping the review gate**: going straight from step-4 phase partitioning into steps 5~7 → the step-4.5 user gate is mandatory (exception: the obvious tiny-task case).
- **Writing code bodies in §4**: writing method bodies/SQL bodies/JS function bodies in phase document §4 → intrudes on `/develop`'s area. Signatures, responsibilities, and dependencies only.
- **Bypassing the step-4.5 review gate**: perfunctorily skipping the phase-partition review and relying only on the auto-trigger flow → a bad partition enters qa-planner as-is. **Step 4.5 is the user-agreement gate right before auto-trigger entry** — no bypassing. Auto-skip of step 4.5 is allowed only for tiny tasks whose partition is obvious.
- **Applying R9 unconditionally**: forcing R9 onto screenless projects such as REST API / Batch / Library and filling the "화면" column with fake entries → R9 is **project-type dependent**. For screenless projects, state that R9 is not applied and use R1~R8 only.
- **Letting R9 beat R3 on conflict**: misreading R9's screen unit as outranking a new domain, and bundling a new-domain screen into an existing-domain phase → **R3 outranks R9**. A new domain gets an independent phase regardless of screen units. (E.g. an add-on domain is a new domain, so it is not bundled into the registration-screen phase.)
- **Violating screen 1:1 (grouping / wizard splitting)**: with R9 applied, bundling screens like *"마법사 3단계는 1 페이즈로 묶기"* or *"CRUD 목록+상세+등록을 1 페이즈로"*, or conversely splitting like *"마법사 1개를 단계별 N 페이즈로 분할"* → violates the single principle **1 screen = 1 phase**. A phase = the user review unit, so bundling screens breaks review separation, and splitting one screen into N scatters the review unit. If a screen is too big, the screen itself should be redefined — it is not a phase-partitioning option (UI flow splitting is outside dev-plan's area).
- **Putting a test phase in dev-plan**: making the last phase "테스트 & DoD" and specifying test class names/scenarios in §3·§4 → intrudes on **qa-plan's area**. Per the R5 correction, no test phase is created. Detailed test planning is owned by the qa-plan per-phase test documents.
- **Violating the 9-section structure (reviving §검증 방법 / omitting §9 DoD)**: a dev-plan phase has the **9-section structure** §1~§7 + §8 (handoff) + §9 완료의 정의(DoD 종료 판정표). Writing §9 DoD but reviving a §검증 방법(테스트 파일·커버리지) section duplicates qa-plan's area — an intrusion. Conversely, omitting §9 DoD leaves the convergence loop with no end-verdict table to check against. §9 DoD is only a *verdict table* (acceptance criteria + verdict-type tags), not a test-code/coverage spec, and the implementer-local completion signals (BE = tests GREEN, FE = sub-agent code-generation completion report) remain the in-phase work-completion signals.
- **Mixing BE+FE in one phase in a full-stack project**: putting Controller·Service·Mapper (BE) together with Template·JS (FE) in one phase → context-switching inefficiency + FE rework risk on API changes + the phase unit becomes ambiguous between the BE work flow and the FE screen unit. **With R10 applied, BE/FE area separation is mandatory**. When R10 is adopted, R9 applies only as the FE phase-partition axis.
- **Narrowing a single-BE-phase slug to a sub-area name**: using the `be-api` / `be-service` slug for a single BE phase, making it look like only part of the area is covered → the single-BE-phase slug is `be`. Only with a multi-stage BE split use `be-{레이어}` or `be-infra` + `be-{도메인}`.
- **Omitting the multi-stage-BE axis choice**: not stating in the §5-2 partition rationale which axis (layer vs domain) was chosen for a multi-stage BE split → the user has to infer "why it was split this way". **Record the axis choice and reason** (infra share, domain count, domain independence) in one line in the partition rationale.
- **≥ 2 bundled domains → applying the domain axis immediately without considering a work-item split**: ≥ 2 domains arrived bundled in one work item, yet the partition goes straight to the domain axis without asking the user *"can the work item be split?"* at step 4.5 → bypasses the operational standard (per-domain work-item separation). **≥ 2 bundled domains makes the step-4.5 preliminary check mandatory** — confirm splittability with the user; if splittable, recommend a dev-interview re-request. Apply the domain axis only after an inseparable verdict (exceptional case only).
- **Forcing the layer axis (≥ 2 domains + high independence + inseparable)**: several confirmed-inseparable, highly independent domains forcibly split into `be-infra` / `be-service` / `be-api` → two domains' code mixes in the `be-service` / `be-api` phases and the review unit blurs. **≥ 2 domains + high independence + inseparable → domain axis** (`be-infra` + `be-{도메인}` × N) as the safety net.
- **Forcing the domain axis (large infra + 1 domain)**: a large infra share with a single domain bundled into one `be-{도메인}` phase → infra work intrudes into the domain phase and the review unit blurs. **Infra ≥ 1d + 1 domain → layer axis** (`be-infra` / `be-service` / `be-api`). The domain axis is only for the ≥ 2 domains inseparable case.
- **Mixing the two axes (layer axis + domain axis in one work item)**: multi-stage BE phases like Phase 2 = `be-service`, Phase 3 = `be-payment` mix the two axes → consistency breaks. **One work item unifies on one axis** (however, `be-infra` is the common entry point of both axes, so the `be-infra` + `be-{도메인}` × N combination on the domain axis is normal).
- **Cutting the substance to fit a length target**: taking the 700-line signal as a norm and shrinking §4 signatures/dependencies, the §5 DB spec, §7 Tasks, and the §9 DoD verdict table → there is no owner in their place, the information disappears, and the implementation agent **fills the gap by inference.** The plan exists to prevent reinterpretation during implementation, so this is not the price of keeping the cap but a defect the cap created — and unlike `529` it does not die loudly; it silently passes QA GREEN. **The only thing to cut is the 6 rows of the `phase-doc-schema.md` 「재서술 금지」 table** — all 6 rows are owned by other documents, so deleting them loses no information.
- **The phase grows while restatements remain**: exceeding 700 lines even after honoring the 「재서술 금지」 6 rows → the phase is too big, so **do not add length; report a phase re-partition to the root.** The order goes this way: ① remove restatements → ② if still over, re-partition. Reversed, whatever is easiest to cut gets cut.
- **Writing the meta JSON only as response text (missing the actual Write)**: stating the `.claude/tmp/dev-plan-meta.json` path in the response text without actually calling the Write tool → the `/dev-plan` skill cannot find the meta file and falls back to the `{task_number}` Fallback. Step 8 is completed by **an actual Bash mkdir + Write tool call**.
- **Old wording remaining in the result return (*"다음 단계 (사용자 명시 호출)"*)**: if, even after the round-1 auto-trigger regression fix, old patterns like *"사용자 명시 호출"* / *"비활성화 권장"* / *"자동 실행 비활성화"* appear in the response itself → the user does not recognize the auto-trigger flow. **Use the step-9 result-return format as-is**; no ad-hoc variants.
- **Copying the DTO field table into the root**: writing the 5-column field table again in root §6-3 → the same contract exists in two places (here and phase §4), and when they diverge there is no way to judge which is right. **Root §6-3 holds only the DTO list and the contract-owning phase.** The field table's single source is BE phase §4-X.
- **Missing the DTO field table in phase §4**: no Request/Response DTO field table (BE phase) or screen input field table (FE phase) in phase document §4-X → the contract exists nowhere (not in the root either). A violation of **phase self-containment** and a loss of contract. The field table inside phase document §4 is mandatory.
- **BE/FE field-name·validation-rule mismatch**: the BE phase §4-X Request DTO field is `userNm` while the FE phase §4-N input name is `userName`, or the validation regexes differ between the two → AJAX payload key mismatch / validation that only one side passes → feature-verification redo. **When writing the FE phase document, Read the BE phase §4-X and grep self-verify** (identical field names / validation rules FE ≤ BE).
- **DoD requires tests GREEN but §3 has no test sources**: a §9 DoD objective (객관) item says "테스트 GREEN" but the §3 implementation-target file list has no test paths → the implementation agent works from §3 alone, so nobody writes the tests, and the DoD stays forever unmet or gets marked GREEN without tests (vacuous GREEN). Measured: this hole forced re-spawning a test-introduction agent mid-phase. **If the DoD requires tests GREEN, put test source paths in §3** — paths only; the spec belongs to qa-plan.
- **FE has stronger validation than BE**: the FE input pattern is a narrower regex than the BE `@Pattern` → legal input the BE accepts is blocked at the FE. Violates the **BE is the final gate** principle. Validation strength FE ≤ BE (FE weaker OK, FE stronger forbidden).

## Final Checklist

- [ ] Were all 11 brief sections parsed and carried into the plan?
- [ ] Was the scope information decided automatically via scope.yaml reverse matching?
- [ ] For a new project, were 1~2 existing projects of a similar type named in the §3-3 pattern reference?
- [ ] Does the phase-count policy match the execution owner? (human execution = R7 recommended 4~7 / orchestrator execution = the minimum count satisfying R6) Are the applied policy and rationale recorded in root §5-2?
- [ ] Does each phase document fill the **9-section** structure (§1~§7 + §8 handoff + §9 완료의 정의), **writing the §9 DoD (end-verdict table)** while **not creating a §검증 방법(테스트 파일·커버리지) section**? (§9 DoD is the convergence loop's end-verdict table / tests·coverage are delegated to qa-plan)
- [ ] Does every Task have a feature unit + time estimate + acceptance criteria?
- [ ] Were the root document + phase documents (N) + meta JSON all written? The meta JSON via a Write tool call, not response text?
- [ ] **Are the 6 rows of the 「재서술 금지」 table absent from the phase documents?** If it still exceeds 700 lines, was a re-partition reported instead of adding length? (Were §4·§5·§7·§9 not shrunk to fit the line count?)
- [ ] Does the result return state the *"자동 트리거"* flow instead of old wording like *"사용자 명시 호출"*?
- [ ] Was the step-4.5 phase-partition review gate passed? (For the obvious tiny-task case, is the skip stated?)
- [ ] Is §4 per-file implementation detail at the signature/responsibility/dependency level, with no method bodies written?
- [ ] Does the result-return guidance state the qa-planner **auto-chained flow** (step-4.5 partition review passes → `/dev-plan` skill dispatch → qa-planner call → qa-planner step 6.5)?
- [ ] For human execution, is the R7 result within the recommended 4~7 range, or if 8+, is the R6 re-examination rationale stated in §5-2? (Not applicable to orchestrator execution — minimum count instead; state "오케스트레이터 최소 페이즈 적용" in §5-2)
- [ ] Is the R9 application status stated? (If applied, the phase table has the "포함 화면" column; if not applied, §5-2 states "R9 미적용 — {이유}")
- [ ] With R9 applied, was R3 (new domain) applied ahead of the screen unit? (Was no new domain absorbed into an existing-domain phase?)
- [ ] Is the **R10 application status** stated? (Full-stack projects require BE/FE area separation; if not applied, §5-2 states "R10 미적용 — 비풀스택")
- [ ] **With R10 applied, were BE/FE not mixed in one phase**? Does the phase table have the "영역(BE/FE)" column?
- [ ] **Is the single-BE-phase slug `be`**, with `be-{레이어}` (`be-infra`/`be-service`/`be-api`) or `be-infra` + `be-{도메인}` (`be-payment`/`be-merchant`) used only for a multi-stage BE split?
- [ ] **For a multi-stage BE split, is the axis choice** (layer axis vs domain axis) stated in the §5-2 partition rationale? (Including a one-line basis: infra share, domain count, domain independence)
- [ ] **If ≥ 2 domains arrived bundled in one work item, was *work-item splittability* confirmed with the user first at step 4.5**? If splittable, was a dev-interview re-request recommended; was the domain axis applied only when inseparable? (The operational standard is per-domain work-item separation; the domain axis is discouraged — exceptional case only)
- [ ] **Is the multi-stage BE split within one work item unified on one axis**? (No axis mixing like Phase 2 = `be-service`, Phase 3 = `be-payment`. However, `be-infra` is the common entry point of both axes)
- [ ] **Was no test phase created**? (R5 correction — tests, verification, regression, coverage, and pass criteria are all owned by qa-plan)
- [ ] Is the phase **§9 DoD (end-verdict table) written** and the **§검증 방법(테스트 파일·커버리지) section not written**? (§9 DoD = an end-verdict table of acceptance criteria + verdict-type tags / test categories, coverage, test class names, and scenarios are not placed in phase documents but delegated to qa-plan)
- [ ] **Does root §6-3 hold only the DTO list and the contract-owning phase, with no copied 5-column field table?** (Field-table single source = BE phase §4-X)
- [ ] **Are both the Request/Response DTO field table in BE phase §4-X** and **the screen input field table in FE phase §4-N** written? (Phase self-containment + contract ownership)
- [ ] **If §9 DoD requires tests GREEN, does the §3 implementation-target file list contain test source paths?** (Without them, nobody writes the tests)
- [ ] **Are the three identical: BE Request DTO field name == FE input name == AJAX payload key?** (grep self-verification recommended)
- [ ] **Is the validation relation FE ≤ BE?** (The FE must not have stronger regexes/length limits than the BE)
- [ ] **Are the column cells of the §5-1 existing-table-usage table written in the `column_name (data_type)` format?** (The data_type is real metadata queried via `information_schema.columns` in the DB-schema-exploration subsection of step-5 §5-3 code exploration)
- [ ] **If §4·§5 contain SQL bodies**, was it verified that the input-argument types of every function (`TO_CHAR`/`TO_DATE`/`CAST`/`||`/arithmetic etc.) are compatible with the column `data_type` per the PostgreSQL function-overload table? (Agent-specific rule — not in the guidelines / especially no calls to nonexistent signatures like `TO_CHAR(varchar, format)` — explicit casting via `TO_DATE`)
- [ ] Were the rules honored: no `.yml/.properties` reading, no `ENC(...)` decryption, no real DB data queries?
