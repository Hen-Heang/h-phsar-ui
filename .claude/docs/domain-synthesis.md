# 도메인 합성 절차 (we-init·domain-update 공용)

> **①결정론 스캔+카탈로그 → ②후보 확정 → ③domain-sync(초회) → ④티어링+fan-out(LLM 저작) → ⑤domain-sync(재실행) → ⑥자동 게이트 → ⑦검수** 순서로 도메인 분석 번들(`.claude/docs/domain/` 페이지 + `index.md`)을 만드는 전체 절차의 단일 출처다. we-init 최초 생산과 domain-update 갱신이 이 절차를 그대로 공유하며, 각자 SKILL.md 에 다시 옮겨 적지 않고 이 문서를 참조한다.
>
> v1(스켈레톤만 읽고 LLM이 직접 룰·흐름을 다 뽑던 절차)과 다른 점: **구조(누가·무엇을·어느 테이블을 만지는가)는 엔진이 결정론으로 스캔·표로 만들고, LLM은 그 표의 "의미"(업무 규칙 요약)만 채운다.** 구조 파트는 재실행해도 항상 같은 결과가 나오고(결정론), 의미 파트는 LLM이 채운 값이 재실행 후에도 보존된다.

```
① 결정론 스캔+카탈로그: we-adp analyze-structure {root} --format catalog --out .we-adp/structure-catalog.json
   (인스턴스 project.yaml 의 structure.entrypoints[] 커스텀 진입점 신호가 자동 반영된다)
①.5 코드 그래프 색인(조건부 — codebase-memory-mcp 있을 때만): index_repository(최초)/detect_changes+증분(갱신)로
   지식그래프를 최신화 → ④ fan-out 이 trace_path·query_graph 로 흐름을 깊게 판다.
   도구 없으면 건너뛴다(스켈레톤 근사 흐름으로 폴백 — 기존 동작, 무해).
② 후보 확정(있으면): 카탈로그 candidates[] 를 사용자에게 확인
   (예: "@BatchMark 가 12개 클래스에 반복 — 배치 진입점인가요?")
   → 확정분을 project.yaml 의 structure.entrypoints 에 저장 → ① 재실행
③ we-adp domain-sync {root}: 모듈 페이지 카탈로그 표·tables/·index 원장 블록을 결정론 생성/병합
   (재실행해도 "의미" 컬럼과 블록 밖 본문은 보존된다)
④ 티어링·fan-out (LLM): 카탈로그 행의 "의미" 컬럼 + 룰·흐름 저작 (담당 서브에이전트가 frontmatter domain 도 부여)
⑤ we-adp domain-sync 재실행: ④가 부여한 frontmatter domain 값으로 index 의 도메인→테이블,
   domains/*.md 의 테이블 블록이 채워진다
⑥ we-adp verify-domain-rules {root}: 인용 실재 + taxonomy 축 + 백링크 + 의미 빈칸 집계
⑦ 검수(1회·자동): 완성 번들 품질 다듬기 — 분류 정합·빈칸 재도전·잘린 설명·고아 도메인.
   변경 시 verify(또는 domain-sync+verify) 1회 재실행
```

## ① 결정론 스캔 + 카탈로그

메인 에이전트(또는 domain-update 스킬)는 먼저 CLI로 프로젝트 전체를 결정론 스캔한다:

```bash
we-adp analyze-structure {projectRoot} --format catalog --out .we-adp/structure-catalog.json
```

이 명령은 스켈레톤(사람이 읽는 요약)이 아니라 **카탈로그**(진입점×테이블×조작을 행 단위로 롤업한 JSON)를 만든다. 카탈로그는 네 부분으로 이뤄진다:

- `modules[]` — 모듈마다 `rows[]`(진입점 행: `symbol`/`method`, `kind`, `route`, `tables[]`, `ops[]`, `evidence`). 진입점에서 도달 가능한 매퍼 쿼리를 호출 그래프로 추적해 그 진입점이 실제로 만지는 테이블·조작(select/insert/update/delete)을 모아 담는다.
- `tables[]` — 테이블별 역방향 집계(어느 모듈·어느 진입점이 이 테이블을 쓰는가). `domain-sync` 가 `tables/` 색인을 만들 때 이 배열을 그대로 쓴다. 리터럴 테이블 접근(supabase `.table("x")` 등)도 이 배열에 합류한다 — 진입점 도달성과 무관하게 접근 테이블이 목록에 뜬다(fw-supabase 신호).
- `candidates[]` — 팩·인스턴스 신호에 없는 애노테이션인데 **서로 다른 클래스 3개 이상**에서 반복 등장한 것들. 배치 잡 마커처럼 사내 관행으로 진입점을 표시하지만 아직 팩이 모르는 애노테이션을 잡아내기 위함이다. 판정은 여기서 하지 않는다(엔진은 세지만 이름 붙이지 않는다) — ②에서 사람이 확정한다.
- `entities[]` — 선언적 ORM 엔티티↔테이블 매핑(SQLAlchemy `__tablename__`, JPA `@Entity`/`@Table`). 각 항목 `symbol`(엔티티 클래스)/`table`/`module`/`evidence`. ④ 티어링·의미 저작 때 도메인 엔티티·테이블 파악에 참고한다. (JPA/QueryDSL 은 레포지토리 엣지로 진입점에 테이블이 귀속된다 — 기존 매퍼 쿼리 방식과 동등하다. 파이썬 SQLAlchemy 도달성은 후속 D2b.)

**인스턴스 커스텀 진입점 신호**: `project.yaml` 의 `structure.entrypoints[]`(각 항목 `annotation`/`kind`/`level`)와 레거시 `batch.jobAnnotation` 이 자동으로 스캔에 반영된다. 즉 ②에서 확정한 애노테이션은 다음 ① 재실행부터 후보가 아니라 정식 진입점으로 카탈로그에 잡힌다.

## ①.5 코드 그래프 색인 (조건부 — codebase-memory-mcp)

카탈로그·스켈레톤의 **호출 흐름은 얕은 정적 근사다**(단일 경로, `maxFlows`·`maxDepth` 상한 — 분기·병렬·다중홉을 다 담지 않는다). codebase-memory-mcp 지식그래프(tree-sitter AST → 함수·클래스·호출사슬)가 있으면 ④ fan-out 이 이 약점을 깊은 다중홉·데이터흐름·cross-service 조회로 메운다. 이 단계는 **그 조회를 하기 전에 그래프를 최신 상태로** 맞춘다.

**조건부 — 도구 없으면 통째로 건너뛴다**: codebase-memory-mcp MCP 도구(`index_status`·`index_repository`·`detect_changes`·`trace_path`·`query_graph`·`get_code_snippet`)가 이 세션에서 호출 가능할 때만 수행한다. 도구는 CLI 설치 시 user 스코프로 등록된다(`engine/src/install-memory.ts` `registerUserScopeMcp`) — 정상 설치면 모든 세션에서 잡힌다. **호출 불가면**(등록 실패·프록시 차단·바이너리 없음) 조용히 이 단계와 ④의 그래프 증강을 건너뛰고, 스켈레톤 근사 흐름만으로 진행한다(기존 동작 — 결정론 카탈로그가 완전성·인용을 그대로 보증하므로 게이트에 지장 없다).

**최신화 절차**:
1. `index_status` 로 이 프로젝트 색인 유무·신선도를 확인한다.
2. **색인이 없으면**(첫 we-init) `index_repository(<projectRoot>)` 로 전체 색인한다 — 무거운 1회 비용(tree-sitter 풀 파싱). 이후는 재사용된다.
3. **색인이 있으면**(domain-update 갱신) `detect_changes` 로 바뀐 파일만 잡아 **증분 재색인**한다 — 매번 풀 재색인하지 않는다(여기가 갱신 효율의 핵심).

> **용어 주의 — "재색인" 두 가지**: 여기의 **그래프 재색인**(`index_repository`/`detect_changes`, codebase-memory-mcp 지식그래프)은 ③⑤의 **도메인 재색인**(`domain-sync`, `docs/domain/` 원장·`tables/`)과 다른 것이다. 둘은 층위가 다르다 — 그래프는 코드 인텔리전스 substrate, 도메인 원장은 문서 색인.

> **한계(과신 금지)**: 그래프도 정적 tree-sitter 분석이라 동적 디스패치·리플렉션·프레임워크 매직은 여전히 사각이다(카탈로그와 같은 종류의 한계, 더 깊을 뿐). "진짜 런타임 흐름"이 아니다 — 실행 트레이스가 필요하면 codebase-memory-mcp `ingest_traces` 는 별도 작업이다.

## ② 후보 확정 (있으면)

`candidates[]` 가 비어 있지 않으면, 메인 에이전트는 각 후보를 사용자에게 확인한다: "`@BatchMark` 가 12개 클래스에 반복 등장합니다 — 배치 진입점인가요, 아니면 다른 용도인가요?" 사용자가 진입점이라 확정하면 그 애노테이션·종류(`http`/`scheduler`/`listener`/`batch`)·레벨(`class`/`method`)을 `project.yaml` 의 `structure.entrypoints[]` 에 기록하고 ①을 다시 실행한다. 확정하지 않은 후보는 무시하고 넘어간다(다음 domain-update 때 다시 나타날 수 있다 — 무해하다).

## ③ domain-sync (초회) — 카탈로그 표·역색인 생성

```bash
we-adp domain-sync {projectRoot} [--packs {ids}]
```

`domain-sync` 는 ①이 만든 JSON 파일을 입력으로 받는 게 아니다 — **같은 결정론 스캔을 내부에서 다시 수행**하므로 ①과 동일한 카탈로그 기준으로 `.claude/docs/domain/` 아래를 **결정론으로** 쓴다(①의 `--out` 파일은 사람·LLM이 보는 참고용이고, ② 확정분이 `project.yaml` 에 저장돼 있으면 여기서도 자동 반영된다). 사람이 손으로 만드는 게 아니라 매번 이 명령이 만들고 병합한다:

- **모듈 페이지 카탈로그 표** — 진입점이 있는 모듈마다 `modules/<모듈-slug>.md` 를 만들거나(없으면 뼈대 생성) 그 안의 `## 카탈로그` 블록을 갱신한다. 표 컬럼은 `| 진입점 | 종류 | 라우트/트리거 | 테이블 | 조작 | 근거 | 의미 |` 고정이다. "라우트/트리거" 칸은 HTTP 진입점이면 라우트 경로, 아니면(스케줄러·컨슈머·배치) 크론식이나 토픽명 등 애노테이션 인자를 그대로 보여준다. **"의미" 칸만 LLM 소유** — 재실행해도 이미 채운 값은 그대로 보존되고(키는 `종류 진입점` 조합으로 매칭), 나머지 컬럼은 매번 스캔 결과로 덮어쓴다.
- **`tables/` 역색인** — 테이블마다 어느 모듈·몇 개 진입점이 쓰는지 보여주는 표. 300행 단위로 `tables/catalog.md`, `tables/catalog-2.md` … 로 쪼갠다.
- **`index.md` 원장 블록**(`index.md` 가 이미 있을 때만) — 뒤에서 설명하는 `<!-- catalog-ledger -->`·`<!-- domain-tables-index -->` 블록.
- **`domains/*.md` 테이블 블록**(그 슬러그의 도메인 페이지가 이미 있을 때만) — 뒤에서 설명하는 `<!-- domain-tables -->` 블록.

이 시점(초회)에는 모듈 frontmatter 의 `domain:` 이 아직 비어 있으므로 도메인→테이블 집계는 비거나 부분적이다. ④에서 서브에이전트가 `domain:` 을 채운 뒤 ⑤에서 다시 돌려야 완전해진다.

## ④ 티어링 + fan-out (LLM 저작)

구조(①③)는 이미 결정론으로 끝났다. 이 단계는 그 구조에 **의미**(이 진입점이 왜 있고 어떤 업무 규칙을 지키는가)를 채우는 LLM 저작 단계다.

### 티어링 (메인 에이전트)

메인 에이전트는 도메인 저작을 직접 하지 않고 **오케스트레이터**가 된다. 카탈로그의 모듈 목록을 보고 각 모듈을 티어링한다:

- **`도메인` 티어 — 반드시 방문**: 그 모듈에 카탈로그 행(진입점)이 1개 이상 있다 — 업무 표면이 있다는 뜻이다.
- **`인프라` 티어 — 방문 생략**: 그 모듈에 카탈로그 행이 0개다(진입점 자체가 없다). 프레임워크 배선만 있는 모듈(서비스 디스커버리·게이트웨이 라우팅·캐시·공용 유틸)이 보통 여기 해당한다.
- **애매하면 `도메인`으로 둔다**(방문). 놓치는 것보다 한 번 더 여는 게 싸다.

티어링 결과로 커버리지 원장 초안을 만든다. 이 원장은 아래 "모듈 커버리지" 절의 `index.md` 표로 실린다. **모듈은 디렉터리명이 아니라 경로로 키잉**한다(동명 모듈 충돌 방지 — 예: 한 저장소에 `common` 이 여럿).

### fan-out 단위 (메인 → 서브에이전트)

`도메인` 티어 모듈마다 서브에이전트를 하나씩 띄우는 게 기본이다(Task/Agent 도구). 다만 카탈로그는 업무영역(라우트 접두사·패키지 그룹·`packageSegment`)을 결정론으로 이미 나눠주므로, **카탈로그 행이 30개를 넘는 모듈은 영역 3~5개씩 묶어 서브에이전트를 여러 개** 띄운다(한 서브에이전트가 행 수십~수백 개를 혼자 훑다 컨텍스트가 터지는 걸 막는다). 그 외(행 30개 이하) 모듈은 모듈당 서브에이전트 1개다. 배치 병렬 상한은 10~12개로 둔다(그 이상은 레이트리밋·컨텍스트 폭주 위험).

**서브에이전트 모델**: fan-out 서브에이전트는 오케스트레이터(메인) 모델을 물려받지 말고 **명시적으로 Sonnet(`model: sonnet`)으로 띄운다.** 의미·룰 저작은 Sonnet으로 충분하고, 세션이 Opus여도 서브를 Sonnet에 고정하면 벽시계·비용이 크게 준다. 인용 정밀도는 Sonnet에서 유지되므로 verify 게이트 통과율에 영향이 적다.

서브에이전트 프롬프트에는 스켈레톤 조각이 아니라 **그 모듈(또는 영역 묶음)의 카탈로그 행들**을 넘긴다 — 이미 구조(진입점·라우트·테이블·조작·근거 파일:줄)가 표로 확정돼 있으므로, 서브는 그 표를 보고 근거 파일을 열어 의미만 판정하면 된다.

각 서브에이전트에 다음을 프롬프트로 넘긴다:
- 프로젝트 루트 경로, 대상 모듈(또는 영역 묶음) 경로.
- 담당 분의 카탈로그 행들(진입점·종류·라우트/트리거·테이블·조작·근거).
- 저작 규칙 중 서브가 지킬 부분만 넘긴다 — 등급·출처태그·근거 실재·인용 정밀도·**인용 경로 형식(전체 상대경로, `.../` 축약 금지)**·비밀 안전수칙·환각 금지, 그리고 아래 "의미 저작 규칙"·"업무 어휘·도메인명"(해당 항목은 "저작 규칙(강제)" 절 참고). `index.md` 유무 같은 페이지 생성/번들 구성 규칙은 domain-sync(③⑤, 엔진)·메인 합성 전용이므로 서브에는 넘기지 않는다.
- ①.5 에서 그래프를 색인했으면 **그래프 증강 지시**(아래)도 넘긴다.
- 지시: 담당 행마다 근거 파일:줄을 열어 업무 규칙을 확인하고 아래 "의미 저작 규칙"대로 의미 칸과 `## 핵심`(룰)·`## 흐름` 을 채운다. 그 모듈(또는 영역)의 대표적인 업무 개념을 관찰했으면 `domainName`(신뢰도 포함)도 판단한다 — 이때 아래 "업무 어휘·도메인명"대로 **화면·안내 문구까지 근거로 본다**.

### 그래프 증강 (조건부 — codebase-memory-mcp)

①.5 에서 지식그래프를 색인한 경우에만 적용한다(도구 없으면 이 절 통째 생략 — 서브는 카탈로그 행 + 스켈레톤 근사 흐름만으로 저작한다, 기존 동작). 목적은 **`## 흐름` 의 품질**이다 — 스켈레톤의 얕은 단일경로 근사 대신 그래프로 깊은 실제 사슬을 판다.

- **흐름 심화**: 담당 진입점마다 `trace_path(<진입점 함수>, mode=calls)` 로 다중홉 호출사슬을, `mode=data_flow` 로 데이터가 어느 테이블·경계로 흐르는지 추적한다. 마이크로서비스면 `mode=cross_service` 로 서비스 간 흐름을 잇는다. 이 결과로 `flows[]` 의 `경로`·`관련테이블[]` 을 스켈레톤보다 정확·완전하게 채운다.
- **완전성 교차검증**(선택): `query_graph`(Cypher)로 "이 테이블을 건드리는 함수 전부", "이 진입점의 호출자 전부"를 열거해 카탈로그가 놓친 간접·동적 경로를 보강한다.
- **인용 정밀도**: 근거를 적을 땐 `get_code_snippet(<정규화명>)` 이 주는 정확한 파일:줄 범위를 쓴다 — 그래프 노드가 실제 위치를 들고 있어 인용 품질이 오른다(⑥ 게이트의 인용 실재 검증에 유리).

**경계(불변)**: 그래프는 **흐름·의미 substrate 를 보강할 뿐 구조를 대체하지 않는다.** 카탈로그의 진입점·종류·라우트·테이블·조작 컬럼은 여전히 엔진 소유·권위이고(서브는 "의미" 칸만 수정), ⑥ 게이트도 카탈로그·taxonomy·백링크에 앵커한다. 그래프가 카탈로그와 어긋나면 **카탈로그를 따른다**(그래프는 근사, 카탈로그는 결정론 백본). 그래프 통째 덤프 금지 — 담당 진입점 단위의 목적형 조회만 한다(컨텍스트 폭주 방지). 모든 흐름·룰은 여전히 검증 가능한 파일:줄 근거를 달아야 한다(그래프에서 나왔더라도 소스에 실재해야 한다).

### 의미 저작 규칙 (신설)

서브에이전트는 **담당 카탈로그 행마다** 다음 셋 중 하나로 판정한다:

1. **업무 규칙이 있다** — 의미 칸에 한 줄 요약을 쓴다. 상세 룰은 별도로 모듈 페이지 `## 핵심` 에 기존 저작 규칙 형식(`- [등급][출처태그] 서술 — 근거 \`파일:줄\` "인용"`)대로 적는다.
2. **뻔한 조회·저장이다**(단순 CRUD·배선) — 의미 칸에 `CRUD` 라고만 쓴다. `## 핵심` 에 별도로 나열하지 않는다.
3. **판정 불가**(근거를 봐도 업무 의미를 확신할 수 없다) — 의미 칸을 **빈칸으로 둔다**. 빈칸은 게으른 생략이 아니라 정직한 미완 표시다 — 커버리지 원장(`<!-- catalog-ledger -->`)에 "의미 채움 n/m" 으로 집계되므로 나중에 다시 채우면 된다. 짐작으로 채우지 않는다.

**카탈로그 표의 "의미" 칸 외 다른 컬럼·행은 서브에이전트가 절대 수정하지 않는다** — 진입점·종류·라우트/트리거·테이블·조작·근거는 엔진 소유다(아래 "엔진 소유 블록" 절 참고). 다음 domain-sync 재실행에서 그대로 덮어써지므로 손대도 소용없다.

### 업무 어휘·도메인명 (신설)

카탈로그는 **구조**(진입점·테이블·조작)만 준다. 그 시스템이 스스로를 뭐라 부르는지 — 진짜 업무 이름 — 는 **코드 식별자·테이블명·글로서리에만 있지 않고, 사람이 읽는 문구에 있다.** 폴더명(대개 약어)이나 글로서리 한 줄만 앵커로 삼으면 시스템을 실제와 다른 이름으로 라벨하기 쉽다. 그래서 서브에이전트는 `domainName`(과 업무 어휘)을 판단할 때 데이터 접근·진입점 코드뿐 아니라 다음 **문구 증거**도 함께 읽는다:

- **화면·안내 문구** — 화면 템플릿·프런트 스크립트의 라벨·안내·확인 대화상자 문자열.
- **메시지·상수 문자열** — 소스 코드 안 문자열 리터럴(예외·안내 메시지), 메시지 리소스(다국어·안내 메시지 파일)의 값.

이 문구들에서 **반복 등장하는 업무 명사**(그 시스템·주체·창구를 가리키는 말)를 도메인 용어 후보로 모은다. 특히 시스템의 정체성을 규정하는 위치(로그인 화면 안내, 권한·역할 설명, 신규 등록 확인 문구 등)에 반복되는 명사는 강한 신호다. 서로 다른 개념이 하나의 약어로 뭉뚱그려진 경우(예: 무언가를 **제공·발급하는 주체**와 그것이 **소비되는 곳**은 별개다)는 구분해 적는다 — 코드 약어가 둘을 같은 이름으로 부르더라도 문구가 둘을 구별하면 문구를 따른다.

수집한 업무 어휘는 `domainName`(신뢰도 포함)과 반환의 `tables[]`(project-meta 용어 시드)에 반영한다. 확정은 ⑤의 taxonomy 관문에서 사람이 한다.

각 서브에이전트는 다음 구조로 반환한다:
```
{
  modulePath, domainName(신뢰도 포함),
  meanings[{ key(카탈로그 행 key), text }],   // 의미 칸에 쓸 값들 (또는 판정불가 → 생략)
  rules[{ 등급, 출처태그, 서술, 근거"파일:줄", 인용 }],
  flows[{ 이름, 경로, 관련테이블[], 근거"파일:줄" }],
  tables[],                              // project-meta 용어 시드
  claudeMd{ 역할, 구조, 진입점, 비고 },     // 모듈 CLAUDE.md 재료
  coverageNote,                          // 예: "행 42개 중 3개 판정불가로 보류"
  rulesFound, flowsFound
}
```

각 배치의 반환은 합성 단계까지 메인 컨텍스트에 모아 둔다(중간 배치 결과 소실 금지) — 배치를 10~12개씩 여러 번 돌리는 동안 앞 배치 반환을 지우지 않는다.

## ⑤ domain-sync (재실행) — 도메인 인덱스 채움

④의 반환을 받은 메인 에이전트는 먼저 모듈 페이지에 의미 칸·`## 핵심`·`## 흐름`·frontmatter `domain:` 을 직접 써 넣고(④에서 서브가 돌려준 값 그대로), 아래 "산출물 구조"대로 **`index.md` 를 최초 저작**한다(매트릭스·페이지 목록·소스맵·커버리지 원장 — index 의 최초 생성은 LLM 책임이다. ③은 index 가 이미 있을 때만 블록을 채우므로, 여기서 만든 index 는 바로 다음 domain-sync 재실행이 원장 블록을 채워 준다). 그 다음 `domain-sync` 를 다시 실행한다:

```bash
we-adp domain-sync {projectRoot} [--packs {ids}]
```

이번엔 `index.md` 가 존재하고 모듈 frontmatter 의 `domain:` 값이 채워져 있으므로, 원장·도메인별 테이블 집계가 완전해진다 — `index.md` 의 `<!-- catalog-ledger -->`·`<!-- domain-tables-index -->` 블록과 `domains/<slug>.md` 의 `<!-- domain-tables -->` 블록이 이 값 기준으로 채워진다. `domain:` 은 **유효한 슬러그**(`[a-z0-9][a-z0-9_-]*`, 대소문자 무관)일 때만 반영된다 — 경로 탈출 문자(`../`, 구분자)가 섞인 값은 조용히 무시된다.

메인 에이전트는 fan-out 반환들을 모아 아래 "산출물 구조"대로 `common.md`·`domains/*.md` 를 저작하고, **`config/project-meta.yaml` 도 반드시 신규 저작한다**. 첫 init 엔 아직 이 파일이 없으므로 `config/project-meta.example.yaml` 을 복사한 뒤 도메인 용어로 채운다(플레이스홀더 잔존 금지) — 안 만들거나 example 그대로 두면 `verify-domain-rules` 가 잡는다.

- **교차 관행 dedup**: 여러 모듈이 공통으로 발견한 패턴(예: 개인정보 암호화, 응답 래핑, 커스텀 매퍼 마커, 생성자 주입)은 모듈마다 반복하지 않고 `common.md` 에 한 번만 적는다(대표 근거 1개). 이게 특정 모듈에 룰이 몰려 보이는 착시의 진짜 원인이다.
- crossCutting 은 `common.md` 에, 도메인 개요·흐름은 `domains/<slug>.md` 에, 전체 카탈로그·커버리지 원장은 `index.md` 에. `config/project-meta.yaml` 은 그대로 생산(반환들의 `tables[]`·용어를 도메인 용어·별칭·보안 키워드로 보강).

### 산출물 구조
- `docs/domain/index.md` — 진입점: product×domain 매트릭스 + 페이지 목록 + 소스맵 + 커버리지 원장(전 모듈, `<!-- catalog-ledger -->`) + 도메인→테이블 색인(`<!-- domain-tables-index -->`). 모듈 목록의 각 설명은 **문장·괄호를 온전히** 적는다(중간 절단·미닫힘 괄호 금지 — 길면 문장을 줄이되 잘린 티가 나게 두지 않는다).
- `docs/domain/modules/<모듈-slug>.md` — 모듈당 1장. slug=경로 키잉. `## 카탈로그`(엔진 생성·병합) + `## 핵심`(룰) + `## 흐름`. frontmatter `domain:` 필수(도메인 티어 모듈).
- `docs/domain/domains/<도메인-slug>.md` — 도메인개념당 1장. `<!-- domain-tables -->`(엔진 채움) + 개요·흐름(LLM 저작). frontmatter `domain:` 필수(자기 슬러그와 동일 값).
- `docs/domain/common.md` — §0 플랫폼 공통 관행(dedup 1장).
- `docs/domain/tables/` — 테이블별 역방향 색인(엔진 생성·전량 재생성, 300행 분할: `tables/catalog.md`, `tables/catalog-2.md` …).
- `docs/domain/taxonomy.md` — 도메인 분류 체계(사람 확정, 아래 "taxonomy.md" 절).
- `config/project-meta.yaml` — 용어·별칭·보안 키워드(페이지 아님 — `config/` 산출물). **신규 저작 필수**: 없으면 `project-meta.example.yaml` 복사 후 도메인 용어로 교체(플레이스홀더 잔존 금지). `verify-domain-rules` 가 존재·플레이스홀더를 검사한다.

### 모듈 커버리지 (index.md 에 실음)
| 모듈(경로) | 티어 | 방문 | 룰 | 흐름 | 비고 |
|-----------|------|:---:|:--:|:---:|------|
| src/order-api | 도메인 | ✓ | 5 | 2 | |
| src/admin-web | 도메인 | ✓ | 3 | 1 | 행 80 중 6영역 표본 |
| infra/discovery | 인프라 | – | – | – | 서비스 디스커버리 |

인프라 티어 행은 방문 안 했으므로 룰/흐름/방문에 `–` 표기 유지. 도메인 티어 행은 각 fan-out 반환의 rulesFound/flowsFound/coverageNote 로 채운다. 전 모듈(도메인+인프라)을 빠짐없이 싣는다. 이 표는 **티어·방문·비고**(룰/흐름 수는 유지해도 됨) 위주의 LLM 저작 표다 — 구조·의미의 정량적 완성도(카탈로그 행 수, 의미 채움 n/m, 테이블 수)는 별도로 엔진이 `<!-- catalog-ledger -->` 블록에 자동 채운다. 두 표는 역할이 다르다: 하나는 사람이 보는 "방문 여부·정성 요약", 하나는 엔진이 매 sync 때 갱신하는 "정량 완성도".

### 페이지 형식 (frontmatter + 본문)
(frontmatter: title·type[module|domain|common|index|tables|taxonomy]·product(모듈경로, module만)·domain(**module·domain 타입은 필수** — module 은 소속 도메인, domain 은 자기 슬러그)·tags·sources·updated. 본문: 요약 1줄 → `## 역할·구조`(module) → `## 카탈로그`(module, 엔진 소유) → `## 핵심`(룰) → `## 흐름` → `## 관련` [[백링크]].)

### 무손실 매핑 (기존 4산출물 → 페이지/config)
- domain-map → index(매트릭스·소스맵) + domains/*(개요)
- domain-rules §0 → common.md / §1·§2 → modules/* `## 핵심`
- domain-flows → modules/* `## 흐름`(교차 흐름은 domains/*)
- project-meta.yaml → 구조는 그대로(페이지화 안 함), 값은 이번 fan-out 용어로 신규 저작

### taxonomy.md (신설 — 도메인 분류 확정)

v1 은 taxonomy 축을 손으로 안 만들고 fan-out `domainName` 에서 매번 자동 유도했다. v2 는 `verify-domain-rules` 가 frontmatter `domain:` 값을 검증할 기준이 필요하므로, 도메인 목록을 **한 번 확정해 파일로 고정**한다.

**생성·확정 절차**: ⑤ 합성 때 fan-out 이 돌려준 `domainName` 들을 모아 domain 목록 초안을 만든다 → 메인 에이전트가 초안을 사용자에게 보여주고 **확정받는다**(중복 통합·이름 정리 포함) → 확정된 목록을 `taxonomy.md` 로 기록한다. 이 관문은 도메인명을 **실제 업무 이름으로 교정하는 자리**다: 초안 이름이 폴더 약어나 글로서리 한 줄에서만 왔다면(화면·안내 문구의 업무어 뒷받침이 약하면) 사용자에게 실제 시스템·업무명을 물어 바로잡는다. 확정하며 새로 드러난 업무어는 글로서리(`CLAUDE.md`)·`config/project-meta.yaml` 용어에도 반영하면 다음 재색인의 앵커가 개선된다. 이후 모든 페이지 frontmatter 의 `domain:` 은 **taxonomy.md 등재값만** 쓴다(`verify-domain-rules` 가 강제). 저작 중 새 도메인 값이 필요해지면 임의로 페이지에 적지 않고, 먼저 `taxonomy.md` 에 추가해 사용자 확정을 받은 뒤 쓴다.

**형식**(자구까지 아래와 동일하게 — `verify-domain-rules` 파서가 이 형식을 그대로 읽는다):

```markdown
---
title: 분류 체계
type: taxonomy
updated: YYYY-MM-DD
---

## domain
- <slug> — <한 줄 설명>

## type
- module / domain / common / index / tables / taxonomy
```

`## domain` 아래 각 줄의 `<slug>` 가 등재값이다(줄 앞 `- ` 다음, ` — ` 앞까지). `## type` 은 고정 집합을 사람이 읽기 좋게 적어 두는 절이다(값 자체는 엔진에 하드코딩돼 있어 이 절 문구를 바꿔도 검증엔 영향 없다). `taxonomy.md` 가 없는 번들(v1 산출물)은 이 축 검증을 건너뛴다 — 있으면 강제, 없으면 스킵이다.

### 완전성 (전수·영역-완전)
전체 모드는 모든 도메인 티어 모듈 fan-out. 카탈로그가 이미 행 단위로 전수 나열하므로, 완전성 판정은 "행마다 의미 칸이 판정됐는가"로 단순해진다 — 뻔한 CRUD 는 `CRUD` 로, 판정 불가는 빈칸으로 커버리지 원장에 정직하게 남긴다. index 커버리지 원장에 전 모듈(인프라 포함) 표기.

## ⑥ 자동 게이트

합성 끝에 다음을 실행해 self-check 한다:

```bash
we-adp verify-domain-rules {projectRoot}
```

이 명령은 네 가지를 확인한다:
- **인용 실재**: 페이지에 적힌 `` `파일:줄` `` 인용이 실제 파일·실제 줄 범위를 가리키는지.
- **taxonomy 축**: frontmatter `domain:` 이 있으면 `taxonomy.md` 의 `## domain` 등재값인지, frontmatter `type:` 이 있으면 `{module, domain, common, index, tables, taxonomy}` 안에 있는지(`taxonomy.md` 없는 번들은 이 검사를 건너뛴다).
- **백링크 실재**: 코드펜스 밖의 `[[백링크]]` 가 실제 페이지를 가리키는지.
- **의미 빈칸 집계**: 카탈로그 표의 의미 칸이 빈 행 수를 보고한다(에러가 아니라 정보 — 저작 미완 표시).

broken(인용·taxonomy·백링크 문제) 이 있으면 표면화 → 저작자가 해당 항목을 수정 → 재검증. broken 이 0이면 통과다(의미 빈칸은 통과를 막지 않는다 — 정보성 집계).

## ⑦ 검수 (품질 다듬기 — 1회, 자동)

⑥ 게이트(broken 0)를 통과한 뒤 **한 번** 도는 자동 품질 검수다. ⑥이 "인용·백링크·taxonomy 등재값이 형식상 맞는가"를 봤다면, ⑦은 완성된 위키를 다시 읽고 "**의미가 말이 되는가**"를 다듬는다. **여러 라운드 루프가 아니라 1패스다** — 위키 형태를 다듬는 정상 작업 선을 넘지 않는다(무거운 크리틱 엔진 재도입 금지).

도메인 산출물은 위키 형태(페이지+index+백링크)가 맞으므로, 이런 가벼운 품질 검수는 자연스러운 작업이다. 경계선은 "위키냐 아니냐"가 아니라 "무거운 기계장치(여러 라운드 루프·복잡한 WIKI 엔진)를 다시 끌어들이냐"다.

**모드**: 전부 **자동 적용 + 끝에 요약 보고.** 실행 중 사람에게 멈춰 묻지 않는다. 단, 검수가 가한 변경(특히 taxonomy 병합·개명·제거)은 요약에 반드시 명시한다 — 사람은 보고를 보고 필요하면 되돌린다(domain-update 의 `.bak` 백업). "조용히 뒤집기"가 아니라 "보고하고 자동"이다.

메인 에이전트가 완성된 번들(`.claude/docs/domain/`)과 ⑥ 게이트 리포트를 입력으로, 아래 **고정 4개 체크리스트**를 순서대로 1회 수행한다. 늘리지 않는다.

**1. 분류(taxonomy) 정합**
- `taxonomy.md` 의 `## domain` 등재값 + `index.md` 매트릭스 + 모듈 frontmatter `domain:` + fan-out 이 모은 업무 어휘를 대조한다.
- 겹치거나 사실상 같은 개념(예: 무언가를 발급하는 주체 vs 그것이 소비되는 곳이 한 이름으로 뭉침), 폴더 약어에서만 온 약한 이름을 찾아 **병합·쪼개기·개명**한다.
- 슬러그가 바뀌면: `taxonomy.md` 수정 → 그 값을 쓰던 페이지 frontmatter `domain:` 전파 → 아래 "정착 재실행".
- 판단 작업이므로 수치 상한 대신 **1패스**. 근거가 약하면 손대지 않는다.

**2. 빈칸(의미 칸) 재도전**
- ⑥이 보고한 커버리지 원장의 판정불가(빈) 의미 칸을 대상으로, 각 근거 `파일:줄` 을 **한 번 더** 열어 업무 의미를 확정할 수 있는지 본다.
- 확정되면 의미 칸에 한 줄. 여전히 불확실하면 **빈칸 유지**(억지로 채우지 않는다 — 정직한 미완 표시).
- 상한 **N=20**(최대 20개 재시도. 새 설정 항목이 아니라 이 문서의 고정 상수다). 초과분은 다음 domain-update 로 미룬다.

**3. 잘린 설명 수정**
- `index.md` 모듈 목록 설명에서 중간 절단·미닫힘 괄호를 찾아, 그 설명만 문장·괄호가 온전하도록 다시 쓴다(길면 문장을 줄이되 잘린 티가 나지 않게).

**4. 고아 도메인 처리**
- `taxonomy.md` 등재값 ↔ 실제 페이지 frontmatter `domain:` 을 대조한다.
- (a) 어느 모듈도 안 가리키는 등재값 → `taxonomy.md` 에서 제거.
- (b) taxonomy 에 없는 frontmatter 값(⑥이 broken 으로 잡은 것) → 가까운 등재값으로 교정하거나, 정당하면 `taxonomy.md` 에 추가한다.

**정착(settle) 재실행 — 딱 1회**
- ⑦이 **페이지 본문만** 고쳤으면 `we-adp verify-domain-rules <root>` 를 1회 재실행해 인용이 여전히 성립하는지 확인한다.
- ⑦이 **taxonomy 슬러그**(병합·개명·제거)를 바꿨으면: 참조 페이지 frontmatter 전파 → `we-adp domain-sync <root> [--packs <ids>]` 1회 → `we-adp verify-domain-rules <root>` 1회.
- 어느 경우든 **재실행은 1회**(루프 아님). 재실행 뒤에도 broken 이 남으면 그 항목만 고치고 요약에 남긴다.

**요약 보고**
- 검수 결과를 한 줄로 요약한다. 예: `검수: 도메인 2개 병합 · 빈칸 20개 중 5개 채움 · 설명 3개 수정 · 고아 1개 정리`. 고칠 게 없었으면 `검수: 이상 없음`.

**생략 조건**: 도메인 번들 자체를 생략한 경우(그린필드/얇은 소스, 또는 `recipe:false` 인 미지원 스택)면 ⑦도 생략한다. 단 `recipe:false` 는 결과 보고에 "구조 레시피 없음"을 명시한다(조용한 생략 금지).
**멱등성**: ⑦은 다시 돌려도 이미 깨끗하면 "이상 없음"으로 무해하게 끝난다.

## 엔진 소유 블록 목록

다음 마커로 감싼 블록은 `domain-sync` 가 생성·병합하며, **LLM 은 이 블록 안을 직접 편집하지 않는다**(의미 칸 예외 — 아래 참고):

| 블록 | 위치 | 마커 | LLM 편집 가능 범위 |
|---|---|---|---|
| 카탈로그 표 | `modules/*.md` | `<!-- catalog:begin -->` … `<!-- catalog:end -->` | "의미" 칸만(그 외 컬럼·행은 엔진 소유) |
| 커버리지 원장 | `index.md` | `<!-- catalog-ledger:begin -->` … `<!-- catalog-ledger:end -->` | 없음(전량 엔진 생성) |
| 도메인→테이블 색인 | `index.md` | `<!-- domain-tables-index:begin -->` … `<!-- domain-tables-index:end -->` | 없음(전량 엔진 생성) |
| 도메인별 테이블 | `domains/*.md` | `<!-- domain-tables:begin -->` … `<!-- domain-tables:end -->` | 없음(전량 엔진 생성) |

블록 밖 본문(요약·`## 핵심`·`## 흐름`·`## 관련` 등)은 전적으로 LLM 저작이고 domain-sync 재실행에도 보존된다. `tables/*.md` 파일 전체도 엔진이 통째로 재생성하므로 손으로 편집하지 않는다.

## 저작 규칙 (강제)

티어링·fan-out·합성 전 구간에 적용된다.

- **도메인 이름은 관찰 근거 2개 이상일 때만 단정**(예: 패키지어 + 화면·안내 문구/주석의 업무어). 폴더명·글로서리만으로는 약하다 — 화면·안내·메시지 문구의 업무어를 우선 근거로 삼는다(위 "업무 어휘·도메인명" 참고). 근거가 약하면 `[감지]` 또는 `확인 필요` 로 쓰고 단정형 첫 문장에 쓰지 않는다.
- **룰**(모듈 페이지 `## 핵심`) 한 줄 = `- [등급][출처태그] 서술 — 근거 \`파일:줄\` "인용"`. **등급** `[확실]`/`[추정]`, **출처태그** `[표준]`/`[고유]`. 불확실한 발견은 별도 후보 섹션을 두지 않고 `[추정]` 등급으로 `## 핵심` 안에 표기한다.
- **근거 없는 룰 금지.** 인용한 `파일:줄` 은 실재해야 한다(`we-adp verify-domain-rules` 로 검증 가능).
- **인용 정밀도**: 인용한 `파일:줄` 은 룰의 근거가 되는 **정확한 줄**(SQL 조건·애노테이션·상수 선언)을 가리킨다. 블록/메서드 시작 줄이 아니라, 그 줄을 열어 확인한 실제 위치를 적는다.
- **인용 경로 형식**: 경로는 **프로젝트 루트 기준 전체 상대경로**로 적는다(예: `src/order-api/src/main/resources/mapper/OrderMapper.xml:60`). `.../` 로 중간을 줄이거나 파일명만/메서드명만 적지 않는다 — `we-adp verify-domain-rules` 는 전체 상대경로만 실재 확인할 수 있어, 축약하면 실제 파일이 있어도 "missing file" 로 잡힌다.
- **비밀값 인용 금지**: 인용 줄에 토큰·비번·키·접속문자열이 있으면 값을 빼고 `파일:줄` 만 남기거나 그 룰을 생략한다(비밀 안전수칙).
- `index.md` 없이 모듈/도메인 페이지만 만들지 않는다.

## 소비자 (소스맵 독자)

산출된 도메인 색인(`.claude/docs/domain/`)은 소스 코드의 도메인 의미 지도(소스맵)다. 소스를 탐색·이해하는 SDD 소비자는 탐색 직전 `index.md` → 대상 페이지 순으로 먼저 참조해 출발점으로 삼는다(색인이 없으면 건너뜀). 각 소비자 문서에 절차를 다시 적지 않고 이 규약을 따른다.

## 부록 — fan-out 서브에이전트 shell 안전수칙

④ fan-out 서브에이전트 프롬프트에 아래 내용을 **반드시 포함한다.**

> 실측 사고: 한 번의 fan-out 에서 워크스페이스 루트에 0바이트 쓰레기 파일 14개가 생겼다 — `0`, `1)`, `itr`, `Thread`, `ERR_CD`, `companyGrade`, `orderInfoList)`, `size)`, `userInfo`, `item`, `code`, `()`. 서브에이전트가 자바/SQL 조각을 Bash 인자로 넘겼고, 조각 안의 `>` 가 셸 리다이렉트로 해석돼 그 이름의 파일이 생성된 것이다.

- **코드·SQL 조각을 shell 명령 인자로 쓰지 않는다.** 검색은 Grep 도구, 파일 열기는 Read 도구로 한다. `grep`·`echo`·`cat` 을 Bash 로 돌리면 조각 안의 `>`(제네릭 `List<Item>`, 비교식 `cnt > 0`, `getErrCnt() > 0)`)가 리다이렉트로 해석된다.
- Bash 를 꼭 써야 하면 인자를 **단일 인용부호로 감싸고**(`'...'`), `>` `<` `)` `|` `&` 가 든 문자열은 애초에 넣지 않는다.
- 산출물은 리다이렉트(`> file`)가 아니라 **Write 도구**로 쓴다. CLI 산출물은 `--out` 옵션을 쓴다.
- 서브에이전트는 **자기 담당 산출 파일 외에 어떤 파일도 만들지 않는다.** 실수로 만들었으면 지우고 반환에 적는다.

메인 에이전트는 fan-out 종료 후 **워크스페이스 루트에 0바이트 신규 파일이 생겼는지 확인**한다(`find . -maxdepth 1 -type f -size 0`). 있으면 지우고, 내용이 있는 예상 밖 파일은 지우지 말고 사용자에게 알린다.
