# Concurrency — 동시성 안전 체크리스트

> 외부와 상호작용하는 변경 연산의 멱등성·중복 방어·복구 계약에 관한 원칙.
> 언어·도메인에 무관한 범용 원칙만 다룬다. 구체적 구현 예시는 lang 파일 참조.

---

## CONC-01 — 외부 변경 연산 멱등성

**원칙:**
외부에서 호출 받는 변경 연산(지급·승인·처리 등)은 멱등하게 설계한다. 클라이언트는 네트워크 장애·타임아웃 후 동일 요청을 재시도할 수 있으므로, 서버는 중복 요청을 안전하게 처리해야 한다. 요청 식별자를 사전 조회하여 이미 처리된 요청이면 기존 결과를 반환하고, 저장소 수준의 유일성 제약으로 동시성 경쟁 조건도 차단한다.

**검증 질문:**
- 외부에서 재시도가 들어와도 동일한 효과(단 한 번 처리)가 보장되는가?
- 요청 식별자(또는 멱등 키) 기반으로 중복 처리를 사전 차단하는 로직이 있는가?
- 데이터 저장소의 유일성 제약이 동시 경쟁 조건에서도 중복을 차단하는가?
- 이미 처리된 요청에 대해 기존 결과를 반환하는가?

**심각도:** Critical

## CONC-02 — 비동기 제출 중복 방어

**원칙:**
비동기 요청을 유발하는 UI 액션(버튼 클릭, 폼 제출 등)은 완료 전까지 중복 제출을 방어해야 한다. 사용자 인터페이스 수준에서 진행 중임을 표시하고 추가 제출을 차단하며, 서버 측 멱등성(CONC-01)과 함께 적용한다. UI만으로는 사용자 환경에 따라 우회될 수 있으므로 두 계층 모두 방어해야 한다.

**검증 질문:**
- 제출 후 응답이 오기 전까지 동일 액션이 재실행되지 않도록 UI가 차단하는가?
- 진행 중 상태를 사용자에게 명확히 표시하는가(로딩 표시, 버튼 비활성 등)?
- 서버 측에도 CONC-01(멱등성) 방어가 함께 적용되어 있는가?
- 완료 또는 실패 후 UI 상태가 올바르게 복구되는가?

**심각도:** Critical

## CONC-03 — 외부 노출 변경 API 복구 계약

**원칙:**
외부 시스템에 노출하는 변경 API(지급·승인·취소 등)는 호출 결과를 나중에 확인하고 취소할 수 있는 복구 계약을 함께 제공해야 한다. 외부 시스템이 타임아웃 등으로 응답을 수신하지 못했을 때 직접 상태를 조회하거나 원연산을 취소할 수 있어야 한다.

**검증 질문:**
- 외부에 노출하는 변경 API에 대응하는 원연산 조회 수단이 제공되는가?
- 외부 시스템이 결과를 미수신했을 때 스스로 취소·보상할 수 있는 API가 있는가?
- 변경 API·조회 API·취소 API가 세트로 함께 문서화되어 제공되는가?

**심각도:** Warning
