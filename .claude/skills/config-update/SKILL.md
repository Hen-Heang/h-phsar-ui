# /config-update [project-name-or-path]

Compares the workspace against the three instance config files and applies confirmed differences:

| File | What can change |
|---|---|
| `project.yaml` | `projects[]` add/remove/update (name, shortName, multiModule, role, guideline) |
| `scope.yaml` | scope groups/entries for added/removed/restructured projects |
| `project-meta.yaml` | adopt the filled `.claude/` copy into the instance (drift repair) |
| `CLAUDE.md.part2` | regenerate the `<!-- workspace-inventory -->` block (workspace summary: project count/list/stack) when `projects[]` changes |

Why this skill exists: after `we-init`, nothing updates these files. A new project repo in the workspace is invisible to the harness — `dev-planner` falls back to "unregistered, register after approval", `code-investigator` aborts. Hand-editing `.claude/config/*` doesn't survive `we-adp update`, because `.claude/` is a build artifact of `.we-adp/` (the instance source of truth). This skill edits the source of truth and reassembles.

---

## ★ Preload (always the first step)

1. Read `.claude/config/project.yaml` (current assembled config).
2. Read `.we-adp/composition.yaml` (lang/frameworks — needed for `--packs`; never modified).

If either is missing, this is not an initialized harness — print "run `/we-init` first" and stop. Read `references/sync-rules.md` right before authoring edits (step 6).

---

## Core principles

1. **The instance is the source of truth.** All durable edits go to `.we-adp/config/*.yaml`; `.claude/config/*` is regenerated by reassembly, never edited directly.
2. **Engine does structure, this skill does semantics.** Project/module structure comes verbatim from `we-adp analyze-structure`; the skill authors only semantic labels (shortName, role, guideline, group name, subScope.paramName) — same contract as `we-init` derived asset 1.
3. **One confirmation, always.** Nothing is applied without the single batch confirmation (`AskUserQuestion`). "Apply immediately without asking" cannot be honored — an unconfirmed config change silently redefines what every other skill is allowed to touch.
4. **Every proposed item carries evidence** (directory path, build file, skeleton entry, dead reference). No evidence → not proposed.
5. **Removals are paired.** Removing a project from `projects[]` removes its scope entries in the same apply — a dangling `scopes[].project` reference hard-breaks `/develop`.

### Write contract

| Allowed | `.we-adp/config/project.yaml` · `.we-adp/config/scope.yaml` · `.we-adp/config/project-meta.yaml` · `.we-adp/CLAUDE.md.part2` (only inside the `<!-- workspace-inventory:begin/end -->` block), plus scratch under `.claude/tmp/config-update/` |
|---|---|
| Forbidden | editing `.claude/config/*` directly (build artifact — hash churn, clobbered on update) · `composition.yaml` · `system.yaml` · `settings.json` · `answers.json` · any source file |

## Boundary (what this skill refuses)

- **Stack/pack change** (new language, new framework) → full `/we-init` re-run. This skill never edits `composition.yaml`. A new project whose detected stack is outside the current composition is still registered (it is a workspace member), with a notice that pack guidelines won't cover it.
- **Domain content authoring** (keywordExpansion entries, securityKeywords, `docs/domain/` pages) → `/domain-update`. This skill only carries an already-filled `project-meta.yaml` into the instance.

---

## Input format

```
$ARGUMENTS = [project-name-or-path]
```

Empty → full workspace sync. A project name or path → scan and diff only that project (registered or not). A name/path that matches neither a directory nor a `projects[].name` entry → error with both interpretations tried, stop.

---

## Execution flow

```
1. Preload + gate (above)
2. Argument narrowing
3. Baseline: read .we-adp/config/{project,scope,project-meta}.yaml;
   diff vs .claude/config/ copies → hand-edit "adopt" items
4. Deterministic scan → candidate diff items
5. Proposal + ONE batch confirmation
6. Backup to .claude/tmp/config-update/ + edit .we-adp/config/*.yaml
7. Self-check (references/sync-rules.md)
8. Reassemble: we-adp update --no-self-update  (failure → restore backup, stop)
9. Report + pointers
```

### 4. Deterministic scan

- `we-adp analyze-structure . --packs {composition lang,frameworks} --format scope --out .claude/tmp/config-update/scope-skeleton.json` — the structural ground truth.
- **New-project candidates**: skeleton groups (and top-level directories with a build file or `.git`, excluding `.claude`, `.we-adp`, `{{config.outputDir}}`, `{{config.tempDir}}`, vendored dirs) whose name is not in `projects[].name`. Per candidate, run `we-adp detect {dir} --summary` for stack evidence.
- **Removal candidates**: `projects[].name` entries whose directory no longer exists.
- **Change candidates**: per registered project, skeleton vs `scope.yaml` drift — allowedPaths, sharedModule, subScope, module count (`multiModule` = skeleton group has >1 scopes, never hand-counted).
- **project-meta drift**: `.claude/config/project-meta.yaml` differs from the instance copy → propose adopting the filled version into the instance.
- **CLAUDE.md inventory drift**: the `<!-- workspace-inventory -->` block in `.we-adp/CLAUDE.md.part2` disagrees with `projects[]`, or the markers are missing (legacy part2) → propose regenerating the block.
- `scope.yaml` absent and `features.scope.enabled` false → skip all scope items.

### 5. Proposal + confirmation

Present per-file sections with `[+] add / [-] remove / [~] change` items, each with its evidence. Then **one** `AskUserQuestion`:

- Options: `Apply all (recommended)` / `Choose subset` / `Cancel`. Subset → one follow-up multiSelect question.
- Removal items always state the blast radius: scope entries deleted with it; domain docs untouched (→ `/domain-update`).
- Zero diff items → report "configs already in sync (basis: skeleton diff empty, all project dirs present)" and stop. The judgment itself is never skipped.

### 6–7. Edit + self-check

- Copy the current `.we-adp/config/*.yaml` files to `.claude/tmp/config-update/` first (rollback point).
- Text-edit the instance files — preserve comments, key order, block style. Never re-serialize through a YAML library. New scope entries are copied verbatim from the skeleton; only semantic labels are authored.
- `projects[]` changed (or inventory drift confirmed) → regenerate the `<!-- workspace-inventory:begin/end -->` block in `.we-adp/CLAUDE.md.part2` from the post-edit `projects[]`: one intro line + one bullet per project (name, module shape, role one-liner) + stack/build lines. Markers missing (legacy part2) → wrap only the leading summary facts once. **Never touch prose outside the block** — everything else in `CLAUDE.md.part2` is authored content.
- Run the self-check in `references/sync-rules.md` (scope refs resolve, ids unique, `projects:` block-style, no key loss, removals paired) before reassembly.

### 8. Reassemble

```
we-adp update --no-self-update
```

Validate-first: on validation failure `.claude/` is untouched — restore `.we-adp/config/` from the `.claude/tmp/config-update/` backups, report the validation errors, stop. On success the pipeline regenerates `.claude/config/*`, rewrites install-record hashes, and clears `.claude/tmp/` (the backups go with it — expected).

### 9. Report

```
Config sync applied: {n} item(s)
  project.yaml : +{a} / -{r} / ~{c}
  scope.yaml   : +{a} / -{r} / ~{c}
  project-meta : {adopted | unchanged}
  CLAUDE.md    : {inventory block regenerated | unchanged}

Next steps:
  {if project added}    /domain-update   ← synthesize domain docs + keywords for {name}
  {if project-meta}     we-adp verify-domain-rules .   (run it now and report the result)
  {if hand-edits adopted} note: a one-time .bak of the old .claude copy was created by the update — safe to delete
```
